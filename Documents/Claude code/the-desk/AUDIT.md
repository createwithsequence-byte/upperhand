# THE DESK . UX / Front+Back-End Audit

## 1. Read

THE DESK works as a read-only briefing and the design is genuinely past "good enough" for a single-user local tool. The whole thing is one ~970-line `index.html` reading three files in `data/`, with the "brain" a Claude Code session following `RUN.md`. That architecture is correctly right-sized. Do not add a backend, a database, or a metered-API rewrite.

The single most important fix: **Approve/Pass persists nowhere.** `resolve()` (index.html:919-929) only flips a CSS class, and `load()` cache-busts every refresh (`?v=Date.now()`, line 742), so the one button the entire product exists for forgets every decision on reload. The exact localStorage pattern you need is already written twice in the same file for theme/plain (lines 932-968). Copy it.

Two other items are effectively P0 because they undercut the product's entire honesty premise: vs-SPY is the hardcoded string `"+0.0%"` (lines 793-794) while the real `baseline` block sits unread in portfolio.json (lines 10-15), and the top bar's Value (`port.totalValue` 1367.85) does not reconcile with the denominator the check chips divide by (computed `total`). Everything else is polish, correctly deferrable, or a conscious skip.

## 3. Per-surface notes

### Shell (index.html, the whole app)

The design system is tight: 3 fonts, green/loss palette, fixed grid+glow, sticky bar, working dark/light + plain-English toggles both persisted, smooth-scroll anchors. Gaps are all in the chrome, none break the loop.

- **Front-end:** Bar wraps with no `@media` (the only three target `.checks`/`.roles`/`.logrow` at 306/465/612). Zero `:focus` styles. Boots dark regardless of OS (965). Light-theme `--muted-2` (47) fails AA on `th` (555) and bar keys (240). `scroll-margin-top:96px` (168) is a guess that breaks under the wrapped bar.
- **Back-end:** vs-SPY string at 793-794 is the headline KPI faked; the `baseline` block (portfolio.json:10-15) is the unread fix.
- **Additions:** scroll-spy active state (IntersectionObserver, ~12 lines) and `<header>`/`<main>`/`aria-label` semantics. Both marginal at 4 sections.

### Playbook Check (chips, 800-827; `chip()` 908-914; CAPS 726)

The four chips compute live and correctly fire 3 BREACHes (cash, miner 38%, IREN 14%) against the real book. `cash:0` in portfolio.json (line 7) means the Cash floor chip is effectively all-SGOV via `themeSum.cashlike` (783) . worth knowing the "cash" is one ETF.

- **Bug:** Positions chip's frozen "21 names" string (823) will lie the instant a trade lands. The bar/chip denominator mismatch (P1) is here too.
- **UX:** BREACH chips don't link to the proposals that fix them, though `#prop-p1` is already a live target.
- **Addition:** core/satellite split (the playbook's headline control) can't be computed . there's no `tier` field on any position (confirmed). That's a data-model call for you, not a UI fix; do not ship a chip reading a field that doesn't exist (NaN%).

### Proposals (index.html + proposals.json)

Three JSON files render into the Control Room; Approve/Pass flips a class.

- **Bug (P0):** no persistence (919-929).
- **UX:** no copyable ticket / broker link (924); x/5 always green (424-429) even though p2 is 4/5; plain-English skips the No-action jargon (854-858); no empty state.
- **Addition:** auto-run . see section 4. The honest gap is order PREP, not execution.

### Holdings (table 860-873; `.noact` 524-545; portfolio.json positions)

Competent but under-uses computed data. `cost`, `pnl`, day-$ all built (762-773) then thrown away. No grouping, no subtotals, no totals row, despite `themeSum` and `total` already in scope.

- **Bug:** ARBK -99.9% landmine from `avgCost:3240.09` (178-184).
- **Front-end:** theme grouping + subtotals (M), totals row (S), Cost + day-$ columns (S), color all 5 theme tags (S).
- **UX:** no-action list -> `.logrow` grid.

### Decision Log (875-899; decisions.jsonl)

Billed "the scoreboard" (888) but write-once: render reads only `ts/action/symbol/reason`; every row is `pending`/`logged`; no outcome ever written. `runId` present on all 7 rows, never grouped.

- **Addition (P1):** outcome rows keyed `runId+symbol`, paired in render. `RUN.md:33` already promised this.
- **Back-end:** capture one `{type:"snapshot",runId,portfolioValue,spy}` line per run . that IS your vs-SPY time series, free, no chart needed.
- **Front-end:** group by `runId`.

### Back-end / Automation (data/ + RUN.md)

Three files, static reader, Claude-Code brain. Bones are correct. Four leaks: persistence (P0), faked vs-SPY (P0), `proposals.json` overwritten each run with no archive (P1, but half-solved . decisions.jsonl is append-only so the call+price+reason survive; only the rich five-role prose is lost), and manual runs. The archive is a one-line RUN.md change to write `data/runs/{runId}.json` . do it only if you'll actually re-read old debates, which at weekly cadence you won't.

## 4. What to automate

Direct answer to "can we have a section that is automated?": **Yes, but the automatable section is the data refresh + reasoning + file writes, not execution . and it's gated entirely on one unknown that `RUN.md:38` already names: whether the Robinhood MCP OAuth token survives a headless/cron run.**

The lazy path:

- The brain is already a Claude Code routine (`RUN.md`), so you do not write a standalone script. Point a scheduled agent (`scheduled-tasks` / CronCreate) at "Run the desk" weekly. That is the entire implementation . if auth survives.
- **Test auth FIRST, build nothing until you know.** Run one headless "Run the desk" via the scheduler and watch whether the Robinhood MCP reauths at `get_portfolio`. If it survives, the weekly cron job is done. If it doesn't (the likely outcome . interactive OAuth rarely survives unattended), skip unattended runs entirely and set a calendar nudge. A weekly manual run at this account size is a 5-minute chore; automating around a broken OAuth flow is more work than the chore for years.

Hard caveats, do not cross:

- **Never auto-execute orders.** The NO is baked into the product on three independent layers: the footer (901: "you approve and place every order by hand... No auto-execution"), the project memory ("draft-only; propose->approve->manual order"), and the environment's own computer-use rule ("never execute a trade, place an order"). The `robinhood-trading` MCP does expose `place_equity_order`, which is exactly why the guardrail matters. At $1,400 the blast radius of a bug firing real market orders dwarfs any convenience.
- The on-brand warm middle ground is **order prep, not placement**: Approve -> copy-paste ticket + Robinhood deep link (the P1 ticket finding). If you ever want it richer, have the run session call `review_equity_order` (read-only . returns buying power / est cost, places nothing) and bake the result into proposals.json so the card shows "est. proceeds $58, buying power after: $X". Informational, still zero execution. Later, not now.

## 5. SKIP list (conscious non-builds)

- **A backend / database / metered-API rewrite** . `RUN.md:39` says it too: only justified if this runs 24/7 or ships to someone else. Neither is true. localStorage is the correct ceiling.
- **A markdown parser to read caps out of playbook.md at runtime** . a regex against prose like "Max single position: 12% of the book" breaks the instant you reword it. 3 integers, one author, ~never change. Keep the const + the "in sync" comment.
- **Sort controls on the Holdings table** . 21 rows, one user, fits on screen. Scan the P&L column in two seconds. Theme grouping is the only re-ordering that earns its keep. No `sorttable.js`.
- **Per-row concentration bars** . decorative duplication of the Wt column. If you want one concentration visual, a single stacked theme-weight strip above the table beats 21 inline bars, and even that's optional polish.
- **A vs-SPY line chart / stored SPY time series for plotting** . ~1 data point today. Capture the snapshot rows now (free, one line/run); skip plotting until there are 10+ points. YAGNI.
- **Log filtering UI** . the log is 7 rows, grows ~6/week. Cmd+F is free. Grouping by run is all the navigation it needs.
- **Per-card plain-English toggles** . over-engineering at 3 proposals. The global toggle is right for one user; just fill the No-action `eli5` gap.
- **Mobile swipe-nav on the deck** . the deck is already a vertical scroll-snap container, so a thumb-flick advances slides natively. A JS swipe handler would fight the snap.
- **A skip-to-content link** . on a 4-section page that fits one scroll, the visible-on-focus plumbing isn't worth it. (Landmarks + `aria-label` still are.)
- **Deleting the deck's ~250 lines of dead CSS** . it renders fine; dead CSS costs no runtime. Sweep only if you hand the file to an editor.
- **A breach->proposal matching engine** . 3 chips, hard-code the 3 anchor hrefs.
- **Auto-execution of trades** . see section 4. Keep the human's finger on the trigger.
